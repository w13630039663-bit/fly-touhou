# P0「宽感知」A/B 对照实验报告

> 执行时间：2026-09-16 10:20 – 11:05
> 目的：验证瓶颈诊断报告中的 P0 建议（扩感知 8 通道 → 36 通道）是否真能提升能力
> 一句话结论：**不能。宽口径没有提升，反而降低了上限。P0 假设被自己的实验否定。**

---

## 1. 实验设计

| | A 组（对照） | B 组（实验） |
|---|---|---|
| 感知口径 | v1：4 象限威胁 + 2 全局光流 + 2 本体位置 | wide：原 8 通道 + 8 扇区 × (威胁/接近速度/弹幕密度) |
| 输入通道 | **8** | **32** |
| 输入映射 | `graph.json`（32 细胞 4:1） | `graph32ch.json`（32 细胞 1:1） |
| 图拓扑 | 80 节点 / 1296 边 | 80 节点 / 1296 边（**逐位相同**） |
| CEM 超参 | 80 代 × 64 候选 × 8 精英 × 12 种子 | 同 A |
| 训练种子 | `g*137 + 11 + i*12` | 同 A |
| 可训练参数 | 320 | 320（**没变**） |

**控制变量**：两组唯一差异是感知口径与输入映射。图拓扑、读出层容量、超参、种子全部相同。

**为什么在 80 节点上做**：单局 14.1 ms，比 600 图的 134.3 ms 快 9.5 倍。且既有结论是 600 不如 80（1538.2f vs 1544.9f），没有理由先在慢图上试。

---

## 2. 感知层实现（`src/game/danmaku.js`）

新增 `getWideSensoryInput()`，通过 `options.sensoryMode = 'v1' | 'wide'` 切换，**默认 'v1' 保持线上行为逐位不变**。

- **Ch 0-7**：与原 8 通道逐位同义 → 宽口径是原口径的**严格超集**，不是替换
  - 自检：1500 帧 × 5 种子，Ch0-7 与 v1 偏差 **0**
- **Ch 8-31**：8 个 45° 扇区 × (威胁 looming MAX, 接近速度, 弹幕密度)
  - 扇区 0 = 正前方 (±22.5°)，顺时针；扇区 4 = 正后方

### 中途修正：TTC → 密度

第 3 特征原设计为 time-to-collision，**实测弃用**：

| 指标 | 实测 |
|---|---|
| 视距内弹幕样本 | 70,948 |
| 正在逼近 (approachSpeed > 0.05) | 73.5% |
| 接近速度中位数 | **0.87 px/帧** |
| TTC 通道激活率 | **0.2% ~ 5.6%** |

原因：本场景弹幕多为**垂直下落**而非朝自机飞行，法向接近速度中位数只有 0.87 px/帧，
`ttc = dist/approachSpeed` 长期远超任何合理阈值 → **99% 帧恒为 0，是个死通道**。

换成**弹幕密度**（视距内该扇区全部弹幕数 / 6）后：

| | 修正前 (TTC) | 修正后 (密度) |
|---|---|---|
| 激活率 > 2% 的扇区通道 | 12 / 24 | **18 / 24** |

未激活的 6 个是后方扇区的"接近速度"——那里确实没有正在逼近的弹幕，属物理正确。

## 3. 结果

### 3.1 汇总

| 指标 | A: 8 通道 | B: 32 通道 | 差异 |
|---|---|---|---|
| 训练最佳适应度 | 1209.4 | 1146.8 | -5.2% |
| 测试集均值 (20 种子) | 1314.3 帧 (21.9s) | 1352.4 帧 (22.5s) | **+2.9%** |
| 配对差异**中位数** | — | **-178 帧** | **-13.5%** |
| 胜负 | **胜 13** | 胜 7 | — |
| 打满 1800 帧的种子数 | **9 / 20** | **1 / 20** | — |
| 训练耗时 | 16.2 min | 14.9 min | — |

### 3.2 均值 +2.9% 是假象

逐种子配对数据暴露了真相：

```
  种子      A:8通道   B:32通道    B-A
  80001      1495       684      -811
  80002      1800      1622      -178
  80003       930      1314      +384
  80007       544      1798     +1254   ← A 崩了 B 没崩
  80010       533      1800     +1267   ← 同上
  80018      1800      1314      -486
  80019      1800      1228      -572
```

- 均值被 **80007 / 80010** 两个种子（各 +1250）单方面拉高
- 其余 18 个种子：B 稳定输，典型差距 -178 帧
- 更关键：**A 有 9 个种子打满 1800 帧，B 只有 1 个**

→ **A 的上限明显更高。** 宽口径在中低端种子上偶有改善，但丧失了"把多数种子打到满帧"的能力。

### 3.3 口径本身的中性效应（同一组随机权重，仅换感知）

| 随机权重 | v1 口径 | wide 口径 | 差异 |
|---|---|---|---|
| #1 | 794.1 | 835.8 | +5.2% |
| #2 | 802.2 | 877.6 | +9.4% |
| #3 | 1126.3 | 927.1 | **-17.7%** |

方向不一致、幅度从 +9.4% 到 -17.7% → **单次均值比较方差极大，必须配对**。这也解释了为什么不能用"两组的测试集均值"下结论。

### 3.4 交叉检验（策略与口径的耦合度）

| 组合 | 存活帧 |
|---|---|
| A 权重 + v1 口径 | 1314.3 |
| A 权重 + **wide 口径** | **793.5** （-40%） |
| B 权重 + wide 口径 | 1352.4 |
| B 权重 + v1 口径 | 1137.0 （-16%） |

**A 的权重换到 wide 口径直接崩到 793.5 帧 —— 比 wide 口径下的随机基线（867.0）还差。**
说明 A 学到的策略高度依赖 v1 那 8 个通道的特定结构，不是"通用躲避能力"。

## 4. 结论

### 4.1 主结论

**把感知从 8 通道扩到 32 通道，没有提升能力，反而降低了上限。**

三条独立证据方向一致：配对中位数 -178 帧、胜率 13:7、触顶 9:1。

### 4.2 对瓶颈诊断的修正（重要）

瓶颈诊断报告把 **P0（扩感知）列为最高优先级 ★★★★★**，判断是"眼睛太粗 → 直接解决看不见"。

**本实验不支持这个判断。** 扩感知不是解药。

修正后的候选项只剩两个：
- **P1** 读出层容量（16 → 64，参数 320 → 1280）
- **P4** 让 W 可塑（真正开始学习，代价最大）

而这三条路里，P0 已被实测排除，P1 只是把 320 个旋钮变成 1280 个——**但读出层的输入仍只有 16 个 DN**，信息瓶颈没动。所以 P1 的预期收益也应下调。

**真正没被碰过的只有 P4。**

### 4.3 混杂因素（本实验的已知缺陷）

宽口径同时改了两件事：
1. 通道数 8 → 32
2. **每通道细胞数 4 → 1**（输入冗余降低 4 倍）

所以"B 变差"可能来自**冗余降低**，而非"通道多本身没用"。

要排除这个混杂，需要 **C 组：8 通道 + 每通道只 1 个细胞**（其余 24 个细胞无输入）。
- 若 C ≈ A → 冗余不重要，B 的变差是通道数造成的
- 若 C ≈ B → **变差主要来自冗余损失**，P0 的结论需要重新表述

**未做**（时间成本约 15 min）。

### 4.4 一个意外收获

A 组训练有 9/20 种子打满 1800 帧（45%），这个数字**比预期高**。
说明在 80 节点 + 8 通道 + 320 参数下，系统已经能解决近一半的测试种子——**离天花板可能比想象中近**。

```bash
node experiments/_smoke_wide.mjs                        # 感知层自检
node experiments/train_wide_ab.mjs --mode=v1            # A 组 (~16 min)
node experiments/train_wide_ab.mjs --mode=wide          # B 组 (~15 min)
node experiments/_ab_pairwise.mjs                       # 配对分析
```
